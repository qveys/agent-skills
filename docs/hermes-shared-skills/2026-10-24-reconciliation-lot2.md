## 0. Méthode (PROUVÉ)

- Pour chaque skill : regroupement des copies par `sha_dir` (inventaire), puis comparaison fichier par fichier (`uniq.py` : lignes présentes dans une variante et absentes de la base, + `diff`). Base = la copie la plus récente/riche ; les apports des autres copies ont été fusionnés à la main.
- Constat général : pour les skills dupliqués, les copies de `lecteur/stratege/trader/promo-scout/eclaireur` sont **des états plus anciens** de la copie `default` (les lignes « propres à la variante » sont des reformulations plus courtes de lignes de default, vérifié par grep). Les vrais apports uniques sont listés ci-dessous.
- Contrôles : `python3 -m py_compile` (3 scripts .py : OK), `bash -n` (1 script : OK), validation frontmatter par script (name = dossier, description ≤ 60 car. commençant par « Use when », version, section « When to Use ») : 19/19 OK. Aucune valeur de secret (grep `sk-`, `ghp_`, `xox`, `AKIA` ; seules des références `op://` d'exemple).
- Constat transverse **PROUVÉ** (`hermes_cli/kanban_db.py::kanban_home`, `ls`) : le board Kanban est **partagé entre profils** (`$HERMES_KANBAN_HOME`, sinon la racine `/opt/data`), pas sous le `HERMES_HOME` d'un profil. Plusieurs copies écrivaient `$HERMES_HOME/kanban/...` (faux pour un profil) ; corrigé en `<KANBAN_ROOT>` ; les logs de worker d'un board ≠ default sont sous `kanban/boards/<slug>/logs/`. Le flag `--board <slug>` est **global avant la sous-commande** (prouvé : `hermes kanban --help` ; après la sous-commande → erreur d'usage).
