# Git divergence and dirty working trees

## When to Use

Use when a repository has uncommitted changes, diverged branches, or nested worktrees and the user wants to understand or safely reconcile its state.

## Triage before choosing an operation

1. Resolve the repository root and inspect `git status --short --branch`, `git worktree list --porcelain`, and `git rev-list --left-right --count main...origin/main`. Treat ahead/behind counts as **local tracking-ref data** until `git fetch origin` succeeds; do not describe them as current server state beforehand.
2. Inspect each dirty path and nested worktree separately. A tracked gitlink at `.worktrees/...` can appear modified because the nested checkout moved or has edits; ordinary `git status` at the root does not reveal the nested file changes. Check `git ls-files --stage -- <path>` and `git -C <nested-worktree> status --short --branch`. Do not use submodule commands for a worktree gitlink without a `.gitmodules` mapping.
3. Before fetch, merge, rebase, reset or stash, protect all local work: create and verify a bundle of local branches (`git bundle create <durable-backup>/refs.bundle --branches --tags`; `git bundle verify ...`) and archive both tracked edits (`git ls-files -m -z | tar --null -T - -cf <backup>/modified.tar`) and untracked files (`git ls-files --others --exclude-standard -z | tar --null -T - -cf <backup>/untracked.tar`), plus edited files inside nested worktrees. Copy `.git/index` separately to preserve staging. Keep the backup outside the repository and auto-pruned scratch storage; list archive entries and compare restored file contents, ignoring metadata-only timestamp/mode differences. A bundle alone excludes uncommitted and untracked content.
4. With user authorization, `git fetch origin`, then recompute the counts and common ancestor. Use `git merge-tree --write-tree --name-only main origin/main` to preview actual merge conflicts without changing the working tree; nonzero status is expected when conflicts exist. Compare both sides against `git merge-base main origin/main` before proposing resolutions.
5. Separate mechanical content conflicts from deletion-versus-modification decisions. Ask which fate a deliberately deleted file should have rather than restoring it silently. Present one concrete decision at a time. For additive documents (notes, knowledge files, changelogs), do not resolve only the conflict markers: a branch may have rewritten the *rest* of the file before the merge, silently removing valid content from the other branch. Compare the proposed full file against **both** parents (`git diff --cached HEAD -- <file>` and `git diff --cached origin/main -- <file>`); review every removed claim for factual preservation, including statements attributed to a named source. Keep source/provenance and uncertainty when restoring claims, and distinguish an old summary of a fact from an actual contradiction. Preserve existing chronological entries in place when possible so a moved paragraph is not mistaken for lost information.
6. Stage only the resolved paths and inspect `git diff --cached --name-only` before every commit: `git commit` records the whole index, including files staged by an earlier process. Unstage anything outside the intended paths first. If an unpushed commit already swept them, `git reset --soft HEAD~1`, unstage the extras, and recommit only the intended paths. Do not push that mixed commit. Then inspect `git diff --name-only --diff-filter=U`, `git diff --cached --check -- <resolved-paths>` and the parent-to-result diffs. A clean merge index proves only structural resolution, not semantic completeness. Do not call a simulated or staged merge a completed reconciliation.
7. To make a dirty repository clean, inspect each untracked file before committing it; preserve an unfinished draft and its state as unfinished instead of inventing content. If a nested worktree contains edits, commit its own branch first. When a tracked `.worktrees/...` gitlink points to a checkout of the **same** repository rather than a real submodule, prefer removing that accidental gitlink with `git rm --cached -- <path>` and ignoring `/.worktrees/` instead of updating its pointer: a gitlink without `.gitmodules` makes the root misleadingly dirty and cannot be cloned as an ordinary submodule. Verify the checkout still exists and both `git status --porcelain` outputs are empty afterward.
8. For a dirty main with a small, resolvable divergence, merge on an isolated clean worktree (`git worktree add -b <integration-branch> <durable-path> main`; `git -C <durable-path> merge --no-commit --no-ff origin/main`), resolve and review there, then commit. After verifying a durable backup, `git stash push --include-untracked` in main, `git merge --ff-only <integration-branch>`, and `git stash apply --index` so local edits return; retain the stash until exact files and index state are verified. If apply conflicts, resolve against the backup instead of dropping the stash. Do not pull with `--ff-only` when histories diverge, and do not reset, clean, force-push, or rebase a dirty nested worktree as a shortcut. Verify exact status and remote relation again.

## Synchronisation distante

1. On a request to retrieve remote changes while preserving local work, fetch first; if the remote advanced, preview conflicts with `git merge-tree --write-tree --name-only main origin/main`, then merge without rewriting published history. Distinguish local retrieval from publication: push the named branch(es) without force only when the request also authorizes publishing. Check every relevant worktree branch separately rather than assuming pushing `main` also publishes it.
2. Treat a failed multi-ref push as potentially partial and a failed HTTP push as potentially accepted despite its exit status. Read exact remote heads with `git ls-remote origin refs/heads/main refs/heads/<branch>` before retrying or announcing success; `Everything up-to-date` in an erroring push is not proof of success. If the remote advanced during a push, fetch, preview, merge, and retry without force.
3. When an HTTP request is rejected for size, measure the outbound pack (for example `printf 'main\n^origin/main\n' | git pack-objects --stdout --revs --thin | wc -c`) and locate which **commit** introduces the large blobs. Uploading the blobs under unrelated paths in a synthetic temporary branch does not necessarily shrink the final push: Git still traverses and packs the oversized commit. If one unpublished commit exceeds the upload limit, request explicit permission before rewriting it and its descendants. With permission, follow [large-push-recovery](references/large-push-recovery.md): split that commit on an isolated branch, verify exact tree preservation, and push its actual new ancestry in bounded increments, then update `main` without force.
4. Confirm the target branch advanced with `git ls-remote` before announcing success. Only after that, align the clean local branch, verify exact local/remote heads and both worktree statuses, then delete transfer refs. Keep a verified bundle and report incomplete sync candidly if the target still cannot be pushed.

If reconciliation is a prerequisite in an interrupted workflow, route the user's go-ahead back to the original task with the initial goal, blocker, and decision; a detached follow-up without this context can complete Git work while losing the original goal. For a user-facing status, distinguish what was backed up, fetched, simulated, merged, committed, and pushed. State explicitly what remains unresolved.
