# Split an unpublished oversized commit for bounded Git pushes

Use only with explicit authorization to rewrite the affected commit and its descendants. Preserve a verified bundle and a local backup ref pointing to the original branch; never force-update published history. This procedure applies when a *single commit's outbound pack* exceeds the transport limit, not merely when the sum of many small commits is large.

1. Fetch and inspect exact refs. Measure the full pack and suspected commit separately with `printf '<commit>\n^<commit>^\n' | git pack-objects --stdout --revs --thin | wc -c`. Identify the last local commit before any merge of remote history, plus local commits after that merge. Confirm the oversized commit is unpublished. Save `git bundle create <backup>/before.bundle --all`, verify it, and keep the original tip under a local backup ref. Check the main checkout and nested worktrees are clean before changing history.
2. Create a separate worktree and branch from `<large-commit>^`. Apply only the oversized commit with `git cherry-pick --no-commit <large-commit>`, then `git reset --mixed` in that **isolated** worktree to leave its complete result in the working tree while staging nothing. The reset must not run in a checkout containing unrelated edits.
3. Enumerate changed paths with `git diff --name-only --no-renames -z <large-commit>^ <large-commit>`; read their exact mode and object IDs from `git ls-tree -r -z <large-commit>`, and sizes through `git cat-file --batch-check`. Group the large blobs into conservative upload-size batches, leaving small changes for a final commit. For each batch, stage the original objects at their **original paths** using `git update-index --add --cacheinfo <mode>,<oid>,<path>`, and commit; stage deletions with `git update-index --force-remove -- <path>`. This index-based staging preserves content and modes even for a gitlink or a deleted path. After the last commit, require `git rev-parse HEAD^{tree}` to equal `git rev-parse <large-commit>^{tree}` and require a clean worktree.
4. Push each new batch commit in ancestry order to a newly named temporary remote branch; after each push, verify that remote ref, especially if the command reports an HTTP error. These commits must be the **actual ancestors** of the eventual final branch: simply pre-uploading the same blobs in unrelated synthetic commits does not establish a common commit graph and can leave the final outbound pack unchanged. Stop on a rejected batch; reduce the size rather than repeatedly retrying a structural size failure.
5. Cherry-pick local commits from after the original large commit up to the first historical remote merge; verify that the resulting tree matches the corresponding original pre-merge tip. Fetch current `origin/main`, preview with `git merge-tree --write-tree --name-only`, then merge it into the split branch. Resolve content and delete/modify conflicts by rechecking both parents and any previously approved resolution, not by blindly taking one side. Cherry-pick subsequent local-only commits and compare the final tree against the saved original `main` tree; if the remote advanced in the meantime, compare relative to a controlled merge of that new remote state instead. Do not substitute a matching commit count for this tree check.
6. Push the completed split branch to the temporary remote ref first, then push its tip to `refs/heads/main` as a normal fast-forward. Confirm both refs with `git ls-remote`. Only then, with a clean checkout and matching old/new trees, align local `main` to the pushed commit, fetch and verify local/remote equality and all worktree statuses. Delete the temporary remote branches and verify their absence. Retain the original branch/bundle until the replacement is proven sound.

Report separately: whether content was preserved by exact tree equality, which branches reached the server, whether the local checkout and nested worktrees are clean, and whether any transfer refs remain.
