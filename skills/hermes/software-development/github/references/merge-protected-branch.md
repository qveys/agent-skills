# Fusionner une PR sur une branche protégée

- JAMAIS `--admin`, jamais de contournement de règle/ruleset/check. Cause du blocage = à trouver et résoudre.
- Méthodes autorisées : squash ou rebase uniquement — JAMAIS de merge commit (historique linéaire, commits signés). Titre = convention emoji + conventional commits, semantic-release en dépend.
- Le jeton bot ne peut souvent PAS lire `branches/main/protection` ni `GET /rulesets` (403 « Resource not accessible by integration ») : un 403 ne prouve PAS l'absence de règle. Diagnostiquer avec ce qui est lisible : `gh pr view --json mergeStateStatus,statusCheckRollup,reviewDecision`, `compare/main...HEAD` (`behind_by`), check-runs par commit (`commits/<sha>/check-runs`), fils de revue non résolus.
- `GET /repos/O/R/rulesets/<id>` (id lu dans la liste des rulesets, ou fourni par Settings → Rules) répond SOUVENT alors que `branches/main/protection` et `GET /rulesets` renvoient 403 : c'est la source des paramètres réellement appliqués (`allowed_merge_methods`, `required_review_thread_resolution`, `required_approving_review_count`, `require_last_push_approval`). Le lire avant de conclure sur un `mergeStateStatus: BLOCKED` — et se souvenir que le serveur reste l'autorité : l'API REST de merge applique la protection et accepte quand `gh pr merge` refuse.
- Checklist avant merge : check-runs du SHA tous `success`/`skipped`, `behind_by=0` (sinon `POST pulls/<n>/update-branch` puis re-CI ; si l'app reçoit 404 : `git rebase origin/main` + `git push --force-with-lease`, relancer la CI et attendre le nouveau SHA), aucun fil `CHANGE_REQUESTED`, `mergeable_state` ≠ `dirty`. `mergeStateStatus: BEHIND` = checks requis périmés, pas une règle manquante : rebaser d'abord, ne pas conclure à un blocage de politique.
- `gh pr merge <n> --squash --subject "<titre PR> (#n)"`.
- Si `gh pr merge <n> --squash` refuse alors que checks verts et méthode permise : refaire le MÊME merge par API `PUT repos/O/R/pulls/<n>/merge -f merge_method=squash` (aucune règle n'est contournée, GitHub applique la protection). Un seul refus → passer à l'API ; ne pas relancer `gh pr merge` en boucle sur un état inchangé.
- Blocage « Commits must have verified signatures » : la protection `require_signed_commits` exige que CHAQUE commit de la branche head soit `verified` — même pour un squash (test merge créé par GitHub, doc officielle). Des commits poussés en `git push` CLI (auteur ≠ GitHub App) sont `unsigned` et bloquent. Deux entrées possibles pour des commits `verified:true, committer=GitHub` :
  1. `gh api graphql` avec la mutation `createCommitOnBranch` (fileChanges additions/deletions, syntaxe GraphQL `{ path: "...", contents: "<base64>" }`, pas de JSON ; si payload > ~128 Ko, écrire la mutation dans un fichier et utiliser `gh api graphql --input fichier.json` avec `{"query": ...}`) ;
  2. merge `main` dans la branche via l'endpoint `POST pulls/<n>/update-branch` (merge commit signé web-flow, committer `GitHub`).
  Procédure complète : squasher la branche en UN commit signé `createCommitOnBranch` (parent = `main` courant, additions = chaque fichier du diff final au contenu base64, vérifier `verified:true` ET que `commit.tree.sha` == arbre du head précédent), PATCH la ref `git/refs/heads/<branche>` force=true, relancer CI, puis merge squash. Vérifier `mergeable_state` (reste `behind` si `main` avance entre-temps → re-créer le commit sur le nouveau `main`, l'endpoint update-branch peut être 404 pour l'app).
- Les commits créés par l'API REST Git (`POST git/commits`) ou Content restent `unsigned` : seule `createCommitOnBranch` (GraphQL) donne la signature `GitHub`. Test rapide sur une branche jetable avant toute réécriture.
- Lecture des règles (jeton avec Administration: read) : `gh api repos/O/R/branches/main/protection` + `rulesets/<id>`. qveys/my-supervision : checks stricts (`strict: true` => branche à jour sinon BEHIND, rebaser), `validate` requis, signatures requises, historique linéaire, conversations résolues, `enforce_admins: false`. Le jeton est une GitHub App (qveys-hermes-bot, non admin) : l'API de merge ne contourne rien.
- `gh pr merge` affiche BLOCKED tant que les commits de la PR ne sont pas signés (pas de gpg ici) ; le squash GitHub, lui, est signé (SUPPOSÉ : cause du BLOCKED).
- Après merge : vérifier CI de `main`, tag semantic-release, déploiement ; un échec post-merge se traite, ne s'ignore pas.
