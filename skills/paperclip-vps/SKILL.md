# Paperclip on vps-openclaw — direct routes (validated 2026-07-04)

Connect with `tailscale ssh vps-openclaw` (or `ssh vps-openclaw` when the host key is already pinned). **Resolve the live container once and reuse that value for every container-specific command below** — never re-type a remembered name, it may be stale or belong to another instance. Select **exactly one** container, the application one: `CTN=$(docker ps --format '{{.Names}}' | grep -x paperclip)` — the `-x` anchor matches only the container *named* `paperclip`, so the `paperclip-hindsight-1` sidecar and the out-of-scope `paperclip-bef-*` stack can never land in `CTN`; **if `CTN` comes back empty, stop there** — the name changed, so list the candidates (`docker ps --format '{{.Names}}\t{{.Image}}\t{{.Ports}}' | grep paperclip`), pick the application container on 3100 (the one documented in Topology), assign it to `CTN` yourself, and only then continue; never run the `docker inspect` below or any `docker exec` with an empty `CTN`. Confirm its identity with `docker inspect -f '{{.Name}} {{.Config.Image}}' "$CTN"` before anything else, then keep passing `"$CTN"`. `paperclip-paperclip-1` is only the historical default, so a hard-coded name can inspect or patch the wrong instance (see Disk space below).

## Topology
- Host: `vps-openclaw` (tailnet `100.100.10.60`, hostname srv1453980). SSH: `ssh vps-openclaw` (host key already pinned in `known_hosts`; on a fresh machine, verify the host fingerprint out-of-band — provider console or `tailscale ssh` — before first connect; do NOT default to `accept-new`, it trusts whatever key a first-connection MITM presents).
- Container: **`paperclip`** (stack `/docker/paperclip`, image `paperclip:local` built from the repo by `make build`; the old `paperclip-paperclip-1` name is gone), API on `100.100.10.60:3100`, UI served same port. A second stack `paperclip-bef-*` (with its own `paperclip-bef-hindsight-1` sidecar) runs alongside — **out of scope, don't touch it**.
- **No direct egress**: `paperclip` sits alone on the Docker network `internal` (172.16.4.2) with no external DNS. Everything outbound goes through `squid-proxy-squid-1` via `HTTP(S)_PROXY=http://squid:3128` + `NODE_OPTIONS=--use-env-proxy`. A `fetch` that skips those vars dies on `getaddrinfo EAI_AGAIN`, not on a timeout.
- Bind mount: host `/docker/paperclip/data` ⇄ container `/paperclip`.
- **The code that actually RUNS is the global install `/usr/local/lib/node_modules/paperclipai/` inside the container** (`node /usr/local/bin/paperclipai run` is PID 1). The npx caches under `/paperclip/.npm/_npx/<hash>/node_modules/@paperclipai/*` are **secondary copies** (11 hashes exist) — reading code there is fine, but runtime patches MUST hit the global install. Don't repeat the mistake of patching only the npx copy.

## Plugins (worker processes)
- Installed plugins live on the volume: `/paperclip/.paperclip/plugins/node_modules/<pkg>/dist/{manifest,worker}.js`. One forked worker per plugin, visible in `/proc/*/cmdline` (`docker exec --privileged -u root` is needed to read `/proc/<pid>/environ`).
- The host spawns workers with a **deliberately minimal env** (`server/src/services/plugin-worker-manager.ts` → `buildWorkerProcessEnv`, `plugin-loader.ts` → `buildPluginWorkerEnv`): `process.env` is never spread in, so anything a plugin needs must be explicitly passed through. Proxy vars were added there 2026-09-11 (commit `9152ea5dc`, unpushed) — before that every `http.outbound` plugin was dead on this host.
- Plugin config test = `POST /plugins/<id>/config/test` → the worker's `onValidateConfig`. Plugin-side error strings are usually catch-alls: `@vectorize-io/hindsight-paperclip` reports "Cannot reach Hindsight at <url>" for *any* failure, DNS included. Reproduce with `docker exec paperclip env -i PATH=... node -e 'fetch(...)'` before believing the message.

## CLI `paperclipai` (inside container)
- Board auth: `docker exec -it "$CTN" paperclipai connect --persona board --token-name <label>` — **interactive** (user completes login; run it in the user's visible pane). Prints a `pcp_board_…` token (30-day expiry). The CLI context profile does NOT persist it for later `docker exec`s — and never put the token in shell history or process args (`-e KEY=…` is visible in `ps`). Write it to a `0600` env file instead (paste via `read`, not on the command line), then pass it with `--env-file`:
  `umask 077; { echo PAPERCLIP_API_URL=http://localhost:3100; printf 'PAPERCLIP_API_KEY=%s\n' "$(read -rs t; echo "$t")"; } > /root/.pcp.env`
  `docker exec --env-file /root/.pcp.env "$CTN" paperclipai …` — `rm /root/.pcp.env` once the session is done.
- Useful: `company list`, `agent list -C <companyId>` (flag is `-C`, not `--company`), `agent get <agentId> --json`, `agent update <agentId> --payload-json '<json>'` (partial payload OK, e.g. just `{adapterConfig}`), `agent resume <agentId>` (clears error status), `heartbeat run -a <agentId> --timeout-ms 90000` (triggers a REAL adapter run with live logs — the best end-to-end validation).
- HTTP API mirror: `/api/*`, `Authorization: Bearer <key>`. **Only ever call it over the tailnet address (`100.100.10.60`, already end-to-end encrypted by Tailscale's WireGuard between authenticated peers) or the container's own loopback (`docker exec`'s `http://localhost:3100`, never leaves the box)** — never bind/forward port 3100 beyond the tailnet, which would put the bearer token on a genuinely cleartext path. Routes: `PATCH /api/agents/:id`, `GET /api/companies/:id/agents`, `POST /api/companies/:id/adapters/:type/test-environment`.

## Logs / DB / secrets
- Server log: `/docker/paperclip/data/instances/default/logs/server.log` (HUGE, ~800MB — always `tail -c 5000000 | grep`, never read whole). Container boot: `docker logs`. Instance config: `instances/default/config.json`.
- DB: embedded postgres, port 54329 **inside container only**, creds hardcoded upstream in server dist `index.js` ~line 306 (look them up there at need — not reproduced here). NO psql binary anywhere (embedded pkg ships only initdb/pg_ctl/postgres). Query via `docker exec node` + the `postgres` npm package from the global install. NOTE: the permission classifier tends to flag direct DB access as credential exploration — prefer the CLI/API route with a board token; it covers almost everything.
- Company secrets: `POST /api/companies/:id/secrets {name, value}` → `local_encrypted`. In adapterConfig, `{type:"secret_ref", secretId, version:"latest"}` is resolved at runtime ONLY for (a) keys under `env`, and (b) fields the adapter's schema marks `meta.secret:true` (fallback table covers ONLY `hermes_gateway: ["apiKey"]`). **openclaw_gateway has no schema → its `password`/`authToken` fields must be PLAINTEXT** (get explicit user consent; do the PATCH from the Mac with the value in a shell var so it's never displayed).
- **`openclaw config get gateway.auth.password | tail -1` returns a TRUNCATED value** (21 chars vs the real 28) — always read secrets from the canonical file: `jq -r '.gateway.auth.password' ~/.openclaw/openclaw.json`. Compare by `shasum` when debugging "password mismatch", never by printing.

## Disk space (vps-openclaw, `/dev/sda1` 193G) — audited 2026-08-20
- Docker on this host uses the **containerd snapshotter**, not the classic `overlay2` driver: images/layers live in `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs` + `.../io.containerd.content.v1.content`, root-only (`0710`), invisible to `du` as `qveys` — use `docker system df` (accurate even non-root) or re-run as root to see the real files.
- Zero-risk wins: `docker builder prune -a -f` (freed 29.45G) then `docker image prune -a -f` (freed 5.265G) — safe **only while the container is running**. If it's ever stopped/removed first, `image prune -a` deletes the custom committed image (line 10) with no rebuild path — never run this while the paperclip container is down.
- `/docker/<instance>/data/instances/default/companies/<Company>/projects/<repo>/.paperclip/worktrees` — one git worktree per Paperclip issue, unbounded growth (TempMailX alone hit 132 worktrees / 8.2G before cleanup on 2026-08-20, on an instance distinct from the container resolved in Topology (`$CTN`) — resolve the real container name with `docker ps --format '{{.Names}}'` first, don't assume it's the same one). **Worktree admin metadata is written from inside the container**, so paths are recorded container-side (`/paperclip/instances/...`), not as the host bind-mount path — running `git worktree` commands from the host on the bind-mount path gives false-positive "prunable" results. Always operate via `docker exec "$CTN" git -C /paperclip/instances/default/companies/<Company>/projects/<repo> worktree ...`. Bulk-remove all of them (user-approved, not automatic): `docker exec -i "$CTN" sh -s` with a heredoc looping `worktree list --porcelain`, **skipping the first entry** (the main working tree — `worktree remove` refuses to remove it) → `worktree remove --force <path>` per remaining entry, then `worktree prune -v`. Freed 8.2G on 2026-08-20 (part of the cumulative df 81%→49% drop from every cleanup in this section combined, not from this step alone).
- `intervalMinutes`/`retentionDays` backup config lives in `instances/default/config.json` **per instance** — each instance has its own file at its own path, and editing the wrong instance's copy leaves the running one unchanged. **Restarting the container does NOT apply a fix if the file itself was never actually edited** — a prior "already fixed" note turned out to be false because it had edited the wrong instance's file (still 60min/30d after restart). Editing this file via `sed -i` in the visible cockpit was **blocked by the Claude Code auto-mode classifier** (config-file edit) — this needs the user to apply it themselves in the pane, no workaround.
- `/home/qveys` on this host isn't just Paperclip data — unrelated files accumulate there too (found/removed a 28G `skool-offline-archive`, 2026-08-20). Always `du -xh --max-depth=1 /` first for the whole picture, **as root** — as `qveys` it silently misses `/var/lib/containerd` (see above) and undercounts Docker-side bloat.

## Patch infrastructure (last resort — diagnose first)
Do not start with a new patch. For adapter_failed / models-not-loading, inspect live OpenCode/Paperclip config and logs first and ask whether an existing patch is the break. Patch `/paperclip/patches/<name>/apply.sh` only after that, with user consent.
- Boot steps: `/opt/paperclip/entrypoint.d/NN-name.sh` **inside the image** (write with `docker exec -u root`; /opt is root-owned). Read its `README.md` before adding. Conventions: `set -uo pipefail`, marker-gated idempotent, fail-SOFT (`exit 0` always), `.bg.sh` suffix = background (races with server module load — never use for server-code patches).
- Patch payloads live on the volume: `/paperclip/patches/<name>/apply.sh` (survive image updates); the boot step just execs them.
- **That 'payloads live on the volume' rule is NOT universal — check before relying on it** (2026-09-11). `git-signed-push-guard` lives in the **repo**: `/docker/paperclip/patches/<name>/`, tracked by git, baked in by `Dockerfile:49` (`COPY patches/ patches/`), and executed from `/app/patches/<name>/apply.sh`. There is **no** `data/patches/` copy (the comment in `entrypoint.d/52-git-signed-push-guard.sh:5` claiming `data/patches/... -> /paperclip/patches/...` is stale — that path does not exist). Consequence: editing the host file changes nothing until `make build`; every container restart until then re-runs the old payload from the image. Resolve which of the two layouts a patch uses (`ls /docker/paperclip/patches/<name>` vs `ls /docker/paperclip/data/patches/<name>` + `grep patches Dockerfile`) before editing anything.
- **`-path "*/companies/*/agents/*"` matches everything BELOW the agent dir, not the agent dir** — the `*` of a `-path` traverses `/`. Combined with `mkdir -p "$agent_dir/instructions"` this made `apply.sh` create an `instructions/` inside every directory it walked, including the ones the previous boot created: **+1 nesting level per container start**. Found 2026-09-11 at depth 26 — 1822 `instructions` dirs for 23 agents (1799 redundant), 3598 byte-identical duplicate files. Fixed in `e645897fb` by anchoring on the agent's `AGENTS.md` (`find -type f -name AGENTS.md`) and dropping `GIT.md` beside it, so no directory is ever created. Use `-mindepth`/`-maxdepth`, or anchor on a file, whenever a `-path` glob is meant to pin one level.
- `/docker/paperclip/data/entrypoint.d/` (volume) is **DEAD** — the entrypoint only reads `/opt/paperclip/entrypoint.d`.
- **Boot steps do NOT survive an image update** (they live inside the image, unlike the payloads on the volume). After any image pull/rebuild: `docker exec "$CTN" ls /opt/paperclip/entrypoint.d/` and reinstall any missing hook (e.g. `42-openclaw-protocol-v4.sh`) from its volume payload before considering the update done.
- Ship scripts to the VPS by `base64 | tr -d '\n'` locally, then `echo <b64> | base64 -d > file` remotely (avoids quoting hell in typed panes).
- **`entrypoint.d` boot steps can't patch root-owned `node_modules` even when the script itself is written as root** (2026-08-17, `42-openclaw-protocol-v4.sh`): the boot step runs non-root at container start, so writes into the global install fail there. Fix: bake the patch in at **build time** instead — `/opt/paperclip/build.d/NN-name.sh` invoked via a `RUN` line in the image's Dockerfile (runs as root during `docker build`). Verified end-to-end for `openclaw-protocol-v4` (global + npx caches patched, `make build && restart`, ~184s rebuild). Prefer `build.d` over `entrypoint.d` whenever the patch touches root-owned paths.

## Agent home layout — two shapes coexist (2026-09-11)
Never assume the agent doctrine files sit at the agent dir root; check where `AGENTS.md` actually is before writing next to it.
- **Flat** (MyHousekeeper, 8 agents): `companies/<Company>/agents/<name>/AGENTS.md`, with `HEARTBEAT.md`, `SOUL.md`, `TOOLS.md`, `MEMORY.md`, plus `life/`, `memory/`, `skills/` alongside.
- **Nested** (the two UUID-named companies, 15 agents): the agent dir contains **only** `instructions/`, and `AGENTS.md`/`HEARTBEAT.md`/`SOUL.md`/`TOOLS.md` all live inside it.
- One-liner that finds every real agent home regardless of shape (23 hits on instance `default`): `docker exec paperclip find /app/data/instances -type f -path '*/companies/*/agents/*' -name AGENTS.md`.
- Practical trap: a cleanup that deletes `<agent>/instructions/` wipes the doctrine of the 15 nested agents. Guard on content, not on the name: `[ -f "$d/AGENTS.md" ] || rm -rf "$d"`.
- Nothing in the app source reads an `instructions/` directory (`git grep` over `*.ts` is empty) — it is a pure convention of the patch, so its contents are only ever reached via the pointer written into `AGENTS.md`.

## `/docker/paperclip` git repo — shared between qveys and root (fixed 2026-09-11)
A `git` run as root (rebase traces: `ORIG_HEAD`, `REBASE_HEAD`) had left 3806 of 7127 tracked files and 817 `.git` entries `root:root`, including `.git/HEAD` — `git commit` as qveys died on `insufficient permission for adding an object to repository database .git/objects`. qveys is **not** a sudoer on vps-openclaw (`sudo` prompts for a password).
- Repaired by group, not by owner: `chgrp -R claude-shared`, `chmod -R g+w`, `chmod g+s` on every directory, plus `git config core.sharedRepository group`. The `claude-shared` group (gid 1001) already contains exactly `qveys,root`.
- The setgid bit is the part that makes it durable: files created **later by root** still land in `claude-shared`, so the drift does not come back. Without `core.sharedRepository=group`, git re-creates its own objects non-group-writable and breaks the sharing again at the next commit.
- **Check `id` in the pane before committing.** During that repair the pane was left as root; committing there would have recreated root-owned objects and signed with root's config instead of `~/.ssh/id_ed25519_signing`. Host-local signing key, never 1Password, on this box.
