# Paperclip on vps-openclaw — direct routes (validated 2026-07-04)

Connect with `tailscale ssh vps-openclaw` (or `ssh vps-openclaw` when the host key is already pinned). **Resolve the live container once and reuse that value for every container-specific command below** — never re-type a remembered name, it may be stale or belong to another instance. Select **exactly one** container, the application one: `CTN=$(docker ps --format '{{.Names}}' | grep -x paperclip)` — the `-x` anchor matches only the container *named* `paperclip`, so the `paperclip-hindsight-1` sidecar and the out-of-scope `paperclip-bef-*` stack can never land in `CTN`; **if `CTN` comes back empty, stop there** — the name changed, so list the candidates (`docker ps --format '{{.Names}}\t{{.Image}}\t{{.Ports}}' | grep paperclip`), pick the application container on 3100 (the one documented in Topology), assign it to `CTN` yourself, and only then continue; never run the `docker inspect` below or any `docker exec` with an empty `CTN`. Confirm its identity with `docker inspect -f '{{.Name}} {{.Config.Image}}' "$CTN"` before anything else, then keep passing `"$CTN"`. `paperclip-paperclip-1` is only the historical default, so a hard-coded name can inspect or patch the wrong instance (see Disk space below).

## Topology
- Host: `vps-openclaw` (tailnet `100.100.10.60`, hostname srv1453980). SSH: `ssh vps-openclaw` (host key already pinned in `known_hosts`; on a fresh machine, verify the host fingerprint out-of-band — provider console or `tailscale ssh` — before first connect; do NOT default to `accept-new`, it trusts whatever key a first-connection MITM presents).
- Container: **`paperclip`** (image `paperclip:local`, built from `/docker/paperclip` via `make build`), API on `100.100.10.60:3100`, UI served same port. Older notes saying `paperclip-paperclip-1` are stale. Unrelated sidecars on the same host: `paperclip-bef-paperclip-1`, `paperclip-bef-hindsight-1`.
- **No direct egress**: `paperclip` sits alone on the Docker network `internal` (172.16.4.2) with no external DNS. Everything outbound goes through `squid-proxy-squid-1` via `HTTP(S)_PROXY=http://squid:3128` + `NODE_OPTIONS=--use-env-proxy`. A `fetch` that skips those vars dies on `getaddrinfo EAI_AGAIN`, not on a timeout.
- **No app-data bind mount.** The only bind is `./data/.config/github-app:/paperclip/.config/github-app:ro`. Application data lives on the named volume mounted at `/app/data` (see Patch infrastructure).
- **The code that actually RUNS is the repo build under `/app`** — PID 1 is `node --import ./server/node_modules/tsx/dist/loader.mjs server/dist/index.js`, running as uid 1000 (`node`), and the live logic is `/app/server/dist/services/*.js` (compiled from `/app/server/src`). Verified 2026-09-10: `grep 'is not a git checkout' /usr/local/lib/node_modules/paperclipai` returns nothing, `/app/server/dist/services/heartbeat.js` has it. The older claim that the global install `/usr/local/lib/node_modules/paperclipai/` is PID 1 is **stale** — check before patching. **For server logic the durable fix is the repo's `/docker/paperclip/server/src/` plus a rebuild (`make build`).** `/app/server/dist/` is the tree PID 1 actually loads, but `/app` is **not** a bind mount: an edit made there is gone on the next `--force-recreate`, and because the checked-out `/app/server/src` can be older than the built `dist`, a blind `make build` can replace a live fix with older code. So land the change in `/docker/paperclip` and rebuild — treat a direct in-container edit as **emergency-only**, never as the record of the fix. Patching the global install or the npx caches leaves the running server on the old code entirely. The global install and the npx caches under `/paperclip/.npm/_npx/<hash>/node_modules/@paperclipai/*` (11 hashes exist) matter only for packages genuinely loaded from them — reading code there is fine, but a patch there does not reach the server. Don't repeat the mistake of patching a copy the process never loads.

## Plugins (worker processes)
- Installed plugins live on the volume: `/paperclip/.paperclip/plugins/node_modules/<pkg>/dist/{manifest,worker}.js`. One forked worker per plugin, visible in `/proc/*/cmdline` (`docker exec --privileged -u root` is needed to read `/proc/<pid>/environ`).
- The host spawns workers with a **deliberately minimal env** (`server/src/services/plugin-worker-manager.ts` → `buildWorkerProcessEnv`, `plugin-loader.ts` → `buildPluginWorkerEnv`): `process.env` is never spread in, so anything a plugin needs must be explicitly passed through. Proxy vars were added there 2026-09-11 (commit `9152ea5dc`, unpushed) — before that every `http.outbound` plugin was dead on this host.
- Plugin config test = `POST /plugins/<id>/config/test` → the worker's `onValidateConfig`. Plugin-side error strings are usually catch-alls: `@vectorize-io/hindsight-paperclip` reports "Cannot reach Hindsight at <url>" for *any* failure, DNS included. Reproduce with `docker exec paperclip env -i PATH=... node -e 'fetch(...)'` before believing the message.
- "Configuration does not match the plugin's instanceConfigSchema" on save/test = the host's ajv check (`services/plugin-config-validator.ts`), before the worker. Classic cause: the secret picker submits `{type:"secret_ref",secretId,version}` for `format: "secret-ref"` fields that plugins declare `type: "string"` (hit by company-wizard 2026-09-23). Fixed host-side in `949656dd1` (validates a copy with bindings collapsed to `secretId`) — no more per-plugin manifest patches like `patches/hindsight-plugin/`. Repro without a board key: `docker exec -w /app/server "$CTN" node --input-type=module -e` importing `/app/server/dist/services/plugin-config-validator.js` + the plugin's `dist/manifest.js`.
- Plugin secret resolution (`secrets.resolve`) needs ALL of: capability `secrets.read-ref` in the manifest, a `{type:"secret_ref",secretId,version}` object (a bare string is rejected), a `companyId`, and a binding at `configPath` (created when the config is saved for that company). Old bundled plugin SDKs send only `{ secretRef }`. Without an echoed `paperclipInvocationId`, the host admits the call only if `companyId` is one of the plugin's configured companies (proactive scopes). `validateConfig` (the Test button) receives no company, so secrets can't be resolved there. Company-wizard fixed via passes 7-8 of `entrypoint.d/37-company-wizard-secret-resolve.sh` (`de4ccc340`). Manifest edits on disk are resynced to the DB at load, with no approval step. **The current host rejects ANY worker→host call without `paperclipInvocationId` while an invocation is active** (`invalidInvocationScope`, even `config.get` with no company) → company-wizard « Failed to load templates: 502 ». Fixed by pass 9 of script 37 (`feb0d52f4`): backports the SDK's `AsyncLocalStorage` echo into the bundled runtime. Host→worker `performAction` used the 30s default RPC timeout; LLM-backed actions (wizard `ai-chat`, ~45s) → « AI wizard failed » 502 + « received response for unknown request id ». Raised to 90s in `routes/plugins.ts` (`f9fc6ffa8`, stays under Cloudflare's 100s). **`push` drops the exec bit**: check `git show --summary` for `mode change` before `make build`.

## CLI `paperclipai` (inside container)
- ⚠️ **The `paperclipai` CLI is NOT installed in the current image** (2026-09-10: `command -v paperclipai` → not found, `/app/cli/dist` absent). Building it in the container is a dead end: `npm run build` in `/app/cli` produces the bundle, but it imports `zod`, `postgres`, `@clack/prompts`… which are absent from the production image. **To get a board key, use the Paperclip UI over the tailnet.** The commands below only apply to an image that ships the CLI.
- Board auth: `docker exec -it "$CTN" paperclipai connect --persona board --token-name <label>` — **interactive** (user completes login; run it in the user's visible pane). Prints a `pcp_board_…` token (30-day expiry). The CLI context profile does NOT persist it for later `docker exec`s — and never put the token in shell history or process args (`-e KEY=…` is visible in `ps`). Write it to a `0600` env file instead (paste via `read`, not on the command line), then pass it with `--env-file`:
  `umask 077; { echo PAPERCLIP_API_URL=http://localhost:3100; printf 'PAPERCLIP_API_KEY=%s\n' "$(read -rs t; echo "$t")"; } > /root/.pcp.env`
  `docker exec --env-file /root/.pcp.env "$CTN" paperclipai …` — `rm /root/.pcp.env` once the session is done.
- Useful: `company list`, `agent list -C <companyId>` (flag is `-C`, not `--company`), `agent get <agentId> --json`, `agent update <agentId> --payload-json '<json>'` (partial payload OK, e.g. just `{adapterConfig}`), `agent resume <agentId>` (clears error status), `heartbeat run -a <agentId> --timeout-ms 90000` (triggers a REAL adapter run with live logs — the best end-to-end validation).
- HTTP API mirror: `/api/*`, `Authorization: Bearer <key>`. **Only ever call it over the tailnet address (`100.100.10.60`, already end-to-end encrypted by Tailscale's WireGuard between authenticated peers) or the container's own loopback (`docker exec`'s `http://localhost:3100`, never leaves the box)** — never bind/forward port 3100 beyond the tailnet, which would put the bearer token on a genuinely cleartext path. Routes: `PATCH /api/agents/:id`, `GET /api/companies/:id/agents`, `POST /api/companies/:id/adapters/:type/test-environment`.

## Disk space (vps-openclaw, `/dev/sda1` 193G) — audited 2026-08-20
- Docker on this host uses the **containerd snapshotter**, not the classic `overlay2` driver: images/layers live in `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs` + `.../io.containerd.content.v1.content`, root-only (`0710`), invisible to `du` as `qveys` — use `docker system df` (accurate even non-root) or re-run as root to see the real files.
- Cheapest reclaim first, in this order: `docker builder prune -a -f` (freed 29.45G) then `docker image prune -a -f` (freed 5.265G). **Neither is zero-risk — re-check both conditions before every run.** `builder prune -a` drops the entire build cache, so the next `make build` starts cold (the 2026-08-17 rebuild measured ~184s warm); that is a time cost, not data loss. `image prune -a` is the destructive one: it removes **every** image that no container references — **any** container counts, running *or* stopped (a stopped one still protects its image), and a tag does **not** protect anything from `-a`. The image is therefore at risk once the container itself is **removed** (`docker rm`, a recreate, or `docker system prune -a`, which deletes stopped containers first and their images second) — then the custom committed image (Topology) is unreferenced and goes with no rebuild path. Two hard rules: never run `image prune -a` in the same breath as removing or recreating the container; and if a specific image must survive a prune, keep a stopped container referencing it, or `docker save -o paperclip-rollback.tar <image>` first and `docker load` to restore.
- `/docker/<instance>/data/instances/default/companies/<Company>/projects/<repo>/.paperclip/worktrees` — one git worktree per Paperclip issue, unbounded growth (TempMailX alone hit 132 worktrees / 8.2G before cleanup on 2026-08-20, on an instance distinct from the container resolved in Topology (`$CTN`) — resolve the real container name with `docker ps --format '{{.Names}}'` first, don't assume it's the same one). **Worktree admin metadata is written from inside the container**, so paths are recorded container-side (`/paperclip/instances/...`), not as the host bind-mount path — running `git worktree` commands from the host on the bind-mount path gives false-positive "prunable" results. Always operate via `docker exec "$CTN" git -C /paperclip/instances/default/companies/<Company>/projects/<repo> worktree ...`. Cleanup is **list-first, remove-second, never bulk-blind** (user-approved, not automatic) — a worktree is the working state of a real Paperclip issue, so deleting an open one's tree discards its work. First, enumerate candidates and read the porcelain fields, **not** just the paths: `docker exec -i "$CTN" sh -s` with a heredoc running `worktree list --porcelain` and printing path + `locked` + `detached` per entry, plus `git status --porcelain=v1 --untracked-files=all --ignored` inside each — plain `git status --porcelain` hides ignored files, and `worktree remove` deletes without complaint a tree whose only content is ignored, so that set has to be inspected too. Second, classify and show the user: **always keep** the first entry (the main working tree — `worktree remove` refuses it anyway), **skip and report** every `locked` entry (unlock it deliberately first, never as a reflex), **skip and report** every `detached` entry (a detached HEAD can carry commits no branch retains, so a tree that looks clean can still be the only copy of that work), and **skip and report** every worktree whose status is not clean — only a tree whose issue is closed, whose status is clean, *and* whose HEAD is on a branch is a removal candidate. Third, remove only the paths the user explicitly approved, **without `--force`**; reserve `--force` for a candidate where the user has confirmed the uncommitted changes may be discarded, since it is required precisely for the dirty trees the classification step already flagged. Then `worktree prune -v`. Freed 8.2G on 2026-08-20 (part of the cumulative df 81%→49% drop from every cleanup in this section combined, not from this step alone).
- Backup config is split across **two** stores, and this is the single biggest trap on this host (cost a full re-audit on 2026-09-16). `instances/default/config.json` holds `database.backup.{enabled,intervalMinutes,dir}` **per instance** — each instance has its own file at its own path, and editing the wrong instance's copy leaves the running one unchanged. But **`database.backup.retentionDays` in that file is never read by anything**: `server/src/index.ts` → `runServerDatabaseBackup` reads retention from the Instance Settings **stored in the database** (`backupSettingsSvc.getGeneral().backupRetention`, logged at startup as `retentionSource: "instance-settings-db"`). The schemas are `.passthrough()`, so a wrong or stray key produces **no error at all**. Consequence: setting `retentionDays: 7` in `config.json` changes nothing, restart or not — that fix was applied 2026-08-20 and was still inert a month later. The real knob is `backupRetention` = a GFS policy `{dailyDays, weeklyWeeks, monthlyMonths}` (code default `7/4/1`), editable only via **Instance Settings → General → Backup Retention** in the UI (takes effect without restart). `intervalMinutes`, by contrast, *is* read from `config.json` — but only at startup, so it needs a container restart. **Ground truth for what is actually applied is the per-run log line**, which prints both: `docker logs <ctn> | grep 'backup complete'` → `"retention":{"dailyDays":…}` plus `prunedCount`. Measured 2026-09-16: `paperclip-bef` ran `14/4/6` with `intervalMinutes: 360` (60 dumps, 11G); `paperclip` ran the `7/4/1` default with the default 60-minute interval (165 dumps, 6.5G). Editing `config.json` via `sed -i` in the visible cockpit was **blocked by the Claude Code auto-mode classifier** (config-file edit) — the user has to apply it in the pane, no workaround.
- **Deleting a directory on this host can leave services looping forever — check for owners first.** The 28G `/home/qveys/skool-offline-archive` removed on 2026-08-20 (below) was the `WorkingDirectory=` of three **user-scope** systemd units (`skool-archive-media.service`, `skool-archive-worker@{1,2}.service`, `RestartSec=5`). They have been restarting every 5s ever since — 167 282 restarts and ~167 500 journal lines per 24h measured 2026-09-16, which buried every real error in the journal for a month. They do **not** show up in `systemctl --failed` (system scope only), and the user manager you want is **qveys's, not root's**: in a root shell `~` is `/root` and `$(id -u)` is `0`, so a bare `systemctl --user` inspects the wrong manager and misses units under `/home/qveys/.config/systemd/user` and `/run/user/1000`. Spell the target out — `XDG_RUNTIME_DIR=/run/user/1000 systemctl --user list-units --all`, or run the check as `qveys` — or spot them in the journal via `_SYSTEMD_UNIT=user@1000.service`. Before `rm -rf` on any sizeable tree here, run `grep -rl '<path>' /etc/systemd/system /home/qveys/.config/systemd/user 2>/dev/null` — `/home/qveys/...` explicitly, never `~`, which resolves to `/root/...` in a root shell — and disable the owners in the same breath.
- `/home/qveys` on this host isn't just Paperclip data — unrelated files accumulate there too (found/removed a 28G `skool-offline-archive`, 2026-08-20). Always `du -xh --max-depth=1 /` first, **as root** — as `qveys` it silently misses `/var/lib/containerd` (see above) and undercounts Docker-side bloat. That `-x` (`--one-file-system`) confines the walk to `/dev/sda1`, so its output is the **root filesystem only, not the whole picture**: it deliberately skips every other mount, so a full disk can hide there. Pair it with `df -hT` for per-mount usage and `docker system df` for the snapshotter, and run the `du` per mount point when a mount other than `/` is the suspect.

## Patch infrastructure (last resort — diagnose first)
Do not start with a new patch. For adapter_failed / models-not-loading, inspect live OpenCode/Paperclip config and logs first and ask whether an existing patch is the break. Patch only after that, with user consent — and first establish which of the two layouts below the patch uses.
- Boot steps: source of truth = **`/docker/paperclip/scripts/entrypoint.d/NN-name.sh`** (tracked in the repo), baked to `/opt/paperclip/entrypoint.d/` by `Dockerfile:97`. Edit the repo file then `make build && restart` — never `docker exec` into the image copy (lost at next rebuild). Read its `README.md` before adding. Conventions: `set -uo pipefail`, marker-gated idempotent, fail-SOFT (`exit 0` always), `.bg.sh` suffix = background (races with server module load — never use for server-code patches).
- Patch payloads: tracked at **`/docker/paperclip/patches/<name>/`**, baked to **`/app/patches/<name>/`** by `Dockerfile:46` (`COPY patches/ patches/`); the boot step just execs `/app/patches/<name>/apply.sh`. **`/paperclip/patches` is NOT a mount** — the only bind is `./data/.config/github-app:/paperclip/.config/github-app:ro`. Anything found under `/paperclip/patches` is a leftover `docker cp` and dies at the next rebuild. (2026-09-01: `52-git-signed-push-guard.sh` still pointed at the old `/paperclip/patches/...` path → payload never ran, 0/150 agents had `GIT.md`; fixed to `/app/patches/...`.) Treat that as one layout, not a rule — verify per patch before editing anything, and note that this repo-tracked layout **is** the build-context case: a payload that must be root-owned from the image's first start belongs in the Dockerfile, not on a runtime volume.
- **That 'payloads live on the volume' rule is NOT universal — check before relying on it** (2026-09-11). `git-signed-push-guard` lives in the **repo**: `/docker/paperclip/patches/<name>/`, tracked by git, baked in by `Dockerfile:49` (`COPY patches/ patches/`), and executed from `/app/patches/<name>/apply.sh`. There is **no** `data/patches/` copy (the comment in `entrypoint.d/52-git-signed-push-guard.sh:5` claiming `data/patches/... -> /paperclip/patches/...` is stale — that path does not exist). Consequence: editing the host file changes nothing until `make build`; every container restart until then re-runs the old payload from the image. Resolve which of the two layouts a patch uses (`ls /docker/paperclip/patches/<name>` vs `ls /docker/paperclip/data/patches/<name>` + `grep patches Dockerfile`) before editing anything.
- **`-path "*/companies/*/agents/*"` matches everything BELOW the agent dir, not the agent dir** — the `*` of a `-path` traverses `/`. Combined with `mkdir -p "$agent_dir/instructions"` this made `apply.sh` create an `instructions/` inside every directory it walked, including the ones the previous boot created: **+1 nesting level per container start**. Found 2026-09-11 at depth 26 — 1822 `instructions` dirs for 23 agents (1799 redundant), 3598 byte-identical duplicate files. Fixed in `e645897fb` by anchoring on the agent's `AGENTS.md` (`find -type f -name AGENTS.md`) and dropping `GIT.md` beside it, so no directory is ever created. Use `-mindepth`/`-maxdepth`, or anchor on a file, whenever a `-path` glob is meant to pin one level.
- `/docker/paperclip/data/entrypoint.d/` (volume) is **DEAD** — the entrypoint only reads `/opt/paperclip/entrypoint.d`.
- Boot steps **now survive image updates** (they are in the repo and re-COPYed on every build) — the old "reinstall the hook by hand after each pull" caveat is obsolete. What does NOT survive: anything placed by `docker cp` into a live container.

## `promisify(execFile)` loses its custom symbol — root cause of MYH-162 (2026-09-10)
- **Symptom**: agents on git-sensitive adapters (`GIT_SENSITIVE_LOCAL_ADAPTER_TYPES`: `claude_local`, `codex_local`, `cursor`, `gemini_local`, `grok_local`, `hermes_local`…) stuck in `status=error` with *"Issue X requested isolated_workspace with git_worktree, but base workspace … is not a git checkout"*. The workspace is perfectly fine.
- **Root cause, measured by instrumenting the probe**: in the server process, `execFile` has **lost its `nodejs.util.promisify.custom` symbol**. Without it, `promisify()` resolves the *first callback value* — `stdout` as a plain string — instead of `{ stdout, stderr }`. Callers then read `result.stdout === undefined`. Captured evidence:
  `resultType: "string"`, `resultPreview: "\".git\\n\""`, `stdoutType: "undefined"`, `hasPromisifyCustom: "undefined"`.
- **Why it was invisible**: the promise *resolves*, so `isGitCheckout()` never reaches its `.catch()` and never logs. `readNonEmptyString(undefined)` → `null` → `false`, silently. **An empty `grep isGitCheckout` on the logs is the symptom, not an all-clear.**
- **It is systematic, not intermittent** (2/2 captured probes failed). Apparent "bursts" are just when heartbeats run. It breaks *every* git-sensitive run, and every `execFile(...).stdout` reader — including the materialization `git clone`, which explains the `git_worktree_base_materialization_failed` entries too.
- **Fix applied 2026-09-10** — normalize once, at the definition, in both `services/heartbeat.ts` and `services/git-credentials.ts`, rather than patching each call site:
  ```ts
  // Do not build this on `promisify(execFileCallback)`: without the custom
  // symbol that promise resolves the first callback *value* (stdout as a plain
  // string) and exposes no `.child` at all — so normalizing the shape afterwards
  // cannot restore cancellation, because there is nothing to copy.
  // Drive the callback API directly instead: the ChildProcess comes back from the
  // call itself, so the promise always carries it.
  const execFile = ((...args: unknown[]) => {
    type Child = { kill?: (s?: unknown) => unknown };
    let child: Child | undefined;
    const promise = new Promise((resolve, reject) => {
      child = (execFileCallback as unknown as (...a: unknown[]) => Child)(
        ...args,
        // execFile attaches stdout/stderr to the error, so rejecting with it keeps
        // the rejected-path contract identical.
        (err: unknown, stdout: string, stderr: string) =>
          err ? reject(err) : resolve({ stdout, stderr }),
      );
    }) as Promise<{ stdout: string; stderr: string }> & { child?: Child };
    if (child !== undefined) promise.child = child;
    return promise;
  }) as unknown as typeof execFileCallback;
  ```
- **Still unexplained**: *what* strips the symbol. No module under `node_modules` reassigns `execFile` or touches `promisify.custom`; plugins never reference `child_process`. Outside the server process — same container, same uid, CJS and ESM, with and without the tsx loader — the symbol is present (`custom=function`). Treat any new `promisify(<node callback API>)` in this codebase as suspect.
- **Debugging recipe that worked**: poll the workspace at 1 Hz while grepping the logs for the failure timestamp. Seeing the workspace healthy at the exact second the server declares it broken is what rules out the filesystem and points at the probe.
- Compounding issue: the recovery route `POST /api/issues/:id/recovery-actions/resolve` answers **404** (8 of 19 calls, plus 5× 400), so agents cannot close their own recovery loop — hence duplicated worktrees (`pr-audit-merge-order` ×4, `auto-assign-unassigned-issues` ×3).
- Agent `status` does move on its own (CEO and Product Owner went `error` → `idle` unaided on 2026-09-10), but not reliably — several stayed stuck for 9 days. If one is still `error` after the underlying cause is fixed, `agent resume` (board key required) is the lever.
- **Fix verified end-to-end 2026-09-10 15:02 UTC**: zero `WorkspaceValidationFailure` after the rebuild, and the My-Housekeeper CEO (`0b44e4bd…`) started its first run since 2026-09-01, passing workspace validation on worktree `MYH-88-…`. VPS commit `f6314abc0`.

## `/docker/paperclip` git repo — shared between qveys and root (fixed 2026-09-11)
A `git` run as root (rebase traces: `ORIG_HEAD`, `REBASE_HEAD`) had left 3806 of 7127 tracked files and 817 `.git` entries `root:root`, including `.git/HEAD` — `git commit` as qveys died on `insufficient permission for adding an object to repository database .git/objects`. qveys is **not** a sudoer on vps-openclaw (`sudo` prompts for a password).
- Repaired by group, not by owner: `chgrp -R claude-shared`, `chmod -R g+w`, `chmod g+s` on every directory, plus `git config core.sharedRepository group`. The `claude-shared` group (gid 1001) already contains exactly `qveys,root`.
